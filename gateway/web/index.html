Performance

Start with the defaults. Cache only public responses; compress text when it helps your visitors.

Response compression

Read the compression guide ↗

Reduce transfer size for public text, JSON, JavaScript, XML, SVG, and WebAssembly responses.

Higher levels use more CPU. Level 4 is a balanced default.
Smaller known-length responses pass through. Text streams without a declared size compress as they arrive.

Applies to proxied public GET responses with status 200, including cache hits. Requests with cookies, authorization, ranges, or upgrades and responses with cookies, existing encodings, private/no-store, no-transform, or event streams pass through. HEAD requests keep origin metadata. Already-compressed files stay unchanged.

Response caching

Read the caching guide ↗

Cache public GET responses that include an explicit origin max-age or s-maxage. Access rules and rate limits still apply on every hit.

These limits cap origin freshness and response size. They do not force an uncacheable response into storage.Every query parameter stays in the cache key. Leave this off for signed, tokenized, or sensitive URLs. Requests with cookies or authorization always bypass; responses with Set-Cookie, private/no-store/no-cache, or unsupported Vary headers are never stored.

Use caching on routes that serve public content. The shared memory cache holds up to 64 MiB and resets on restart.

Availability
Use multiple backends and health checks when you need failover. Maintenance mode temporarily stops normal traffic.
Load balancing & health checks
Choose how requests reach your origins. With health checks enabled, only healthy, non-draining backends receive new traffic.
One origin per line, up to 16 including the first origin.
Affinity uses the verified visitor IP. It moves traffic when a backend is unavailable or draining; clients sharing an IP share affinity.
One row per configured origin. Weights range from 1–100 and apply to weighted, least-active, and affinity selection. Draining stops new requests while existing ones finish; health checks continue.
GET must return 2xx. Redirects are not followed. Backends wait for successful checks before receiving traffic.
If preserving Host, probes use this route's hostname. A * route uses each upstream hostname.
Timeouts & safe failover
Bound upstream waits and optionally try another available backend after a transport failure.
Connect timeout includes DNS, TCP, and TLS for each attempt. Read/write limits apply to individual I/O waits. Failover retries only bodyless GET/HEAD requests before any response starts. Each backend is attempted once; writes, upgrades, HTTP error responses, and certificate verification failures are never retried.
Session request ordering
Hold concurrent requests that share a session cookie so they reach the application one at a time, in order. Use it only for applications whose own session handling breaks under concurrent requests. It is not a fix for login loops, which usually come from cookies or forwarded headers.
Only requests with a Cookie header are queued, and only per cookie value; other visitors stay parallel. The queue is released once the application starts responding, so WebSockets and streams do not block it. A request waiting more than 10 seconds receives 503.
Maintenance & error pages
Give visitors a clear response during planned work or gateway errors. Browser requests that accept HTML receive an EmberGate page; other clients receive plain text. Application error responses pass through unchanged.
Stops new upstream requests and cache hits for this route. Access rules, HTTPS redirects, and rate limits still apply. Existing requests finish; health checks continue. Paused hosts remain unmatched.
503 is recommended and counts toward error metrics/alerts. 200 reports success; use it only for an intentional holding page. Retry-After is a hint, not an automatic refresh or end time.Plain text only, up to 120 title characters and 2000 message characters. HTML is escaped. The title appears on the HTML page; plain responses contain the message.
